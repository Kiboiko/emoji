## Что исправлено

### 0.1. Открытый dev-вход в админку — ЗАКРЫТО

**Было:** `DEBUG: bool = True` по умолчанию в `backend/config.py`, а в `.env` переменная не задавалась вовсе. Из-за этого на проде был открыт `POST /api/auth/dev`, выдающий JWT с `is_admin: true` **любому желающему без пароля**. Проверка `if not settings.DEBUG` внутри обработчика не спасала, потому что DEBUG фактически был `True`.

**Стало:**
- `DEBUG` по умолчанию `False` (`backend/config.py`);
- роут `/api/auth/dev` **регистрируется только при `DEBUG=True`** — при `False` его не существует, а не «он есть, но отвечает 403»;
- `DEBUG` явно прописан в `.env` и `.env.example`.

**Проверка:**
```
DEBUG=false → POST /api/auth/dev  ->  HTTP 404
             /api/auth/dev отсутствует в /openapi.json
             POST /api/auth/telegram  ->  работает
```

### 0.2. Вебхук оплаты без проверки подписи — ЗАКРЫТО

**Было:** в `backend/routes/payments.py` комментарий `# Verify webhook (aiocryptopay handles this)` не соответствовал коду — тело читалось как обычный JSON, подпись не проверялась. Любой мог отправить `POST /api/webhook/crypto` с чужим `order_id` и получить товар бесплатно.

**Стало:** реализована проверка по схеме Crypto Pay API — `secret = sha256(api_token)`, `signature = hmac_sha256(secret, raw_body)`, сверка с заголовком `crypto-pay-api-signature` через `hmac.compare_digest`. Отдельно поправлено: `except Exception` заворачивал 401 в 400 — теперь `HTTPException` пробрасывается как есть.

**Проверка:**
```
без заголовка подписи      -> HTTP 401 {"detail":"Invalid signature"}
с неверной подписью        -> HTTP 401 {"detail":"Invalid signature"}
```

> Роут удаляется целиком на этапе 3 вместе с CryptoBot. До тех пор дыры быть не должно.

### 0.3. Telegram initData без срока годности — ЗАКРЫТО

**Было:** подпись проверялась, но `auth_date` игнорировался — перехваченный initData работал бессрочно.

**Стало:** проверка возраста (`INITDATA_MAX_AGE_SECONDS`, по умолчанию 24 часа) плюс допуск 5 минут на расхождение часов. Сравнение хеша переведено на `hmac.compare_digest` (защита от timing-атак).

**Проверка:**
```
initData возрастом 60 сек      -> HTTP 200, токен выдан
initData возрастом 2.3 суток   -> HTTP 401 "initData expired"
```

### 0.5. Дубликат модели `OrderItem` — УДАЛЁН

`backend/models/order_item.py` объявлял второй класс `OrderItem` с тем же `__tablename__ = "order_items"`, что и `backend/models/order.py`. Файл нигде не импортировался, но любой импорт уронил бы приложение на старте. Удалён.

## Найдено дополнительно (не было в первичном аудите)

### КРИТИЧНО: регистрация новых пользователей была сломана

Колонка `users.is_blocked` создана первой миграцией как `NOT NULL` **без default**, но в модели `User` она отсутствовала. Значит SQLAlchemy не включала её в `INSERT`, и любая попытка создать пользователя падала:

```
asyncpg.exceptions.NotNullViolationError:
null value in column "is_blocked" of relation "users" violates not-null constraint
```

Затрагивало оба пути входа: `/api/auth/telegram` (боевой) и `/api/auth/dev`. **Если прод-база создавалась миграциями, магазин не мог принять ни одного нового покупателя** — работали только те, кто зарегистрировался раньше появления этого расхождения.

**Исправлено:** `is_blocked` добавлена в модель с `default=False` и `server_default=text("false")`. Колонка понадобится для блокировок в этапах 5 и 7.

> **Нужно от заказчика:** дамп боевой БД (хотя бы `pg_dump --schema-only`), чтобы понять, создавалась ли она миграциями. Если да — регистрация не работает прямо сейчас и это надо выкатывать срочно. Если база создавалась через `create_all()` и миграции на проде никогда не запускались, колонки там нет и проблема проявится при первой же миграции.

### `models/__init__.py` не импортировал все модели

Отсутствовали `ReferralTransaction` и `Withdrawal`. Последствия:
- любой модуль с выборочным импортом моделей падал с `InvalidRequestError: expression 'ReferralTransaction.referrer_id' failed to locate a name` (на этом падал `seed.py`);
- `alembic/env.py` делает `from models import *` — неполный список означал, что autogenerate не видит часть таблиц и предложил бы их удалить.

Исправлено: реестр моделей полный.

### `seed.py` был нерабочим

Строка `settings.DATABASE_URL.replace("postgres", "127.0.0.1")` заменяла подстроку и в схеме URL: `postgresql+asyncpg://` превращалось в `127.0.0.1ql+asyncpg://`. Скрипт падал на разборе адреса. Исправлено.

### Healthcheck nginx всегда падал

`wget --spider http://localhost/health` внутри контейнера: `localhost` резолвится в `::1`, nginx слушает только IPv4 → `Connection refused`. Контейнер вечно в статусе `unhealthy`, хотя сервис работает. Это же поведение и на проде. Исправлено на `127.0.0.1`.

### Админ-логин: небезопасное сравнение и брутфорс

- Пароль из `.env` сравнивался обычным `==` — утечка через тайминги. Переведено на `hmac.compare_digest`.
- Не было никакого ограничения попыток. Добавлен простой in-memory лимитер (`LOGIN_MAX_ATTEMPTS`, `LOGIN_ATTEMPT_WINDOW_SECONDS`). При масштабировании на несколько инстансов вынести в Redis.
- `detail=f"Invalid refresh token: {str(e)}"` отдавал наружу внутренности ошибки — убрано.
- Отладочные `print()` заменены на логгер.

### `SQL_ECHO` отделён от `DEBUG`

Раньше `echo=settings.DEBUG` в `backend/database.py` означало, что включение отладки выливает в логи все SQL-запросы вместе с данными. Теперь это отдельный флаг `SQL_ECHO`, по умолчанию выключенный.

## Требуется от владельца проекта (вне кода)

1. **Ротировать все секреты** — они лежали в архиве открытым текстом: `TELEGRAM_BOT_TOKEN`, `CRYPTOBOT_API_TOKEN`, `DB_PASSWORD`, `ADMIN_PASSWORD`, `SECRET_KEY`.

3. Заодно проверить: `crontab -l`, `docker ps`, открытые порты (`ss -tulpn`), systemd-юниты.
4. **Прислать дамп схемы боевой БД** — нужен, чтобы понять реальное состояние `is_blocked` и спланировать этап 1 без риска.
