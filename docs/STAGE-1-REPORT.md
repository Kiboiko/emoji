# Этап 1 — Приведение миграций в порядок. Отчёт

Дата: 2026-09-13. Всё проверено на локальном стенде.

**Цель этапа:** сделать так, чтобы `alembic revision --autogenerate` можно было запускать, не рискуя снести данные. Без этого нельзя добавлять таблицы под подписки и P2P — там 12+ новых сущностей.

---

## Что было

1. **Три таблицы из десяти не имели ни одной миграции** — `digital_items`, `payments`, `withdrawals`. Существовали только потому, что `main.py` вызывал `Base.metadata.create_all()` при каждом старте.

   Проверено на практике: `alembic upgrade head` на чистой базе давал **8 таблиц вместо 11**. Приложение поднималось исключительно за счёт `create_all()`.

2. **`users.is_blocked`** — в БД `NOT NULL` без default, в модели отсутствовала (разобрано в отчёте этапа 0: из-за этого ломалась регистрация).

3. **`order_items.product_id`** — в БД `NOT NULL` + `ON DELETE CASCADE`, в модели `nullable=True` + `ON DELETE SET NULL`.

Итог: первый же `--autogenerate` предложил бы `drop_column('users','is_blocked')`, пересоздание внешнего ключа и создание трёх уже существующих таблиц (на проде — падение с `relation already exists`).

---

## Что сделано

### Миграция `b7c1d2e3f4a5` — baseline трёх бесхозных таблиц

Файл: `backend/alembic/versions/20260913_0001_b7c1d2e3f4a5_baseline_orphan_tables.py`

Создаёт `digital_items`, `payments`, `withdrawals`. **Идемпотентна** — каждая таблица создаётся только если её нет (`sa.inspect(bind).has_table()`). На проде, где они уже созданы через `create_all()`, миграция — no-op; на чистой базе создаёт схему.

DDL списан с **фактического состояния базы**, а не с моделей — чтобы миграция не «починила» попутно то, что мы не собирались менять.

### Миграция `c8d2e3f4a5b6` — устранение расхождений

Файл: `backend/alembic/versions/20260913_0002_c8d2e3f4a5b6_sync_model_drift.py`

**`users.is_blocked`** — проставлен `server_default false`. Миграция работает по обеим возможным историям боевой базы: если колонка есть (база поднята миграциями) — ей добавляется default; если её нет (база поднята только через `create_all()`) — она создаётся.

**`order_items.product_id`** — переведён в `nullable` + внешний ключ пересоздан с `ON DELETE SET NULL`.

> Здесь важно, какая сторона правильная. Права **модель**: при удалении товара заказ обязан сохраниться — состав заказа и так лежит в снапшоте `order_items.product_snapshot`. С прежним `CASCADE` удаление товара из каталога унесло бы за собой позиции заказов, то есть историю покупок и выручку. Это была не косметика, а незаметная мина.

`downgrade()` намеренно **падает с ошибкой**, если в `order_items` уже есть строки с `product_id IS NULL` — возврат к `NOT NULL` потребовал бы их удаления, а молча терять позиции заказов при откате недопустимо.

### `create_all()` убран из `main.py`

Схема теперь управляется только Alembic. Вместо молчаливого досоздания таблиц добавлена проверка `_verify_schema_is_current()`: на старте сравнивается revision в базе с head в миграциях, при расхождении приложение **не стартует** и говорит, что делать.

```
RuntimeError: Схема БД не соответствует коду: в базе revision=отсутствует,
ожидается c8d2e3f4a5b6. Выполните `alembic upgrade head` перед запуском.
```

Так рассинхрон обнаруживается при деплое, а не случайной ошибкой в бою через неделю.

### `docker-compose.override.yml` для локальной разработки

Код backend монтируется в контейнер: правки видны без пересборки, а файлы, созданные внутри (новые миграции от `alembic revision`), остаются на хосте, а не пропадают вместе с одноразовым контейнером. Плюс `--reload` и проброшенный порт 8000 для отладки в обход nginx.

Compose подхватывает файл автоматически. **На боевом сервере его быть не должно** — либо не выкладывать, либо запускать с явным `-f docker-compose.yml`.

## Проверки

| Проверка | Результат |
|---|---|
| `alembic upgrade head` на существующей базе | Прошло, данные целы (4 товара, 2 категории, 3 пользователя) |
| `order_items.product_id` | `nullable=YES`, FK `ON DELETE SET NULL` |
| `users.is_blocked` | `NOT NULL`, `default false` |
| **`alembic revision --autogenerate`** | **`upgrade()` содержит только `pass`** — деструктивных предложений нет |
| `alembic upgrade head` на **чистой** базе | 12 таблиц (11 + `alembic_version`) |
| Схема «чистая база» vs «прод-эквивалент» | **Побайтово идентичны**, 188 значащих строк дампа |
| Старт приложения на неактуальной схеме | Падает с внятной ошибкой, не поднимается |
| Витрина / админка / API / health | HTTP 200, все контейнеры healthy |

Сравнение схем — ключевая проверка этапа: она доказывает, что цепочка миграций теперь воспроизводит ровно то состояние, которое сложилось на проде из «миграции + `create_all()`». Ничего не потеряно и ничего лишнего не добавлено.

Дампы: `docs/db/schema-baseline-prod-equivalent.sql` (до) и `docs/db/schema-after-stage-1.sql` (после).

## ВАЖНО для деплоя

Раньше приложение само создавало недостающие таблицы при старте. **Теперь нет.** Порядок выкатки становится обязательным:

```bash
docker compose -f docker-compose.yml run --rm backend alembic upgrade head
docker compose -f docker-compose.yml up -d
```

Если запустить backend без миграций — он не стартует и напишет об этом. Это сделано намеренно.

## Что осталось открытым

**Нужен дамп схемы боевой БД** (`pg_dump --schema-only`). Локально я воспроизвёл прод-эквивалент, применив сначала миграции, потом `create_all()` — это соответствует истории «миграции запускались». Но возможен и второй вариант: миграции на проде никогда не запускались, база целиком создана через `create_all()`, таблица `alembic_version` пуста.

Обе миграции написаны идемпотентно и отработают в любом из случаев. Но от ответа зависит одно практическое следствие:

- если на проде **есть** `users.is_blocked` — регистрация новых покупателей там сейчас сломана, и этап 0 надо выкатывать срочно;
- если **нет** — регистрация работает, срочности нет.

Пока дампа нет, исхожу из худшего варианта.
