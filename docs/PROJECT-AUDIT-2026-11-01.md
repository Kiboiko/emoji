## Ошибки со скриншота и создание маркета

В историческом [отчёте этапа 1](ACCEPTANCE-STAGE-1.md) установлена прежняя причина `Invalid hash`: Telegram подписывал вход одним ботом, а сервер проверял подпись токеном другого. При текущей проверке реальные `getMe` подтвердили `Funshop_bot` и у backend, и у bot-контейнера; DEBUG выключен. Это проверка конфигурации, а не вход владельца через настоящий Telegram.

Транслитерация не проходит словарную или языковую проверку: допустимы латинские буквы, цифры, пробел и `. _ & -`, длина 3–20. `Magazin Igrushek`, `Kupi_Tut`, `Dobryi-Magazin`, `Ya Prodavets` проверены. Кириллица по действующему правилу по-прежнему запрещена; одинаковые имена нельзя занять повторно без учёта регистра.

Найдены и исправлены дополнительные причины сбоев:

1. Кабинет запрашивал профиль до завершения входа Telegram. Из-за этого мог получать 401 и показывать форму регистрации вместо уже существующего маркета. Начальная загрузка теперь ждёт готовности SDK и окончания входа.
2. Запоздавший 401 от запроса со старым токеном стирал уже новую сессию. Выход применяется только к сессии, с которой отправили запрос. 401 текущего токена по-прежнему завершает сессию.
3. Два одновременных запроса регистрации одного продавца давали 200 и 500. Добавлены блокировка владельца и понятный ответ при конфликте. Гонка двух владельцев за одно имя также обрабатывается без потери уникальности.
4. Два первых входа одного пользователя могли одновременно создавать запись и получать 500 по уникальному Telegram ID. Проигравший запрос теперь получает уже созданного пользователя. Блокировка аккаунта сохраняется.
5. Refresh-токен принимался как обычный Bearer access-токен. Контексты разделены; старые access-токены без поля type продолжают работать. Совместимость с токеном, выпущенным прежней библиотекой, проверена.
6. Подробности внутренних ошибок входа и объект запроса с initData могли попасть в клиентское сообщение/консоль. Клиент получает безопасный текст, в консоль не передаются заголовки входа.

Браузерная регрессия сначала падала на раннем запросе кабинета и очистке новой сессии; после исправлений проходит. На настоящем API стенда пройдена цепочка «подписанный вход → форма → имя латиницей → созданный маркет». Подпись тестовая; реальный клиент Telegram этим не подменён.

## Производительность и бот

- При активном продвижении сортировалась вся обычная выдача. Продвигаемые товары теперь выбираются отдельной частью страницы; остальная выдача использует индекс. Приоритет оплаты, суточный порядок и явные сортировки сохранены. Пагинация на границе промо/обычных товаров проверена без повторов и пропусков.
- Для рейтинга автора карточка товара собирала все ID товаров магазина в Python и передавала их обратно в SQL. При большом каталоге это загружало API. Теперь набор и агрегация остаются в PostgreSQL; оценки и окно отзывов сохранены. Добавлен тест, ограничивающий число SQL-параметров при росте магазина.
- Бот проверяет действие, номер сделки и UUID заявки до передачи callback в backend. Некорректный callback получает ответ, а не необработанный ValueError. Права по-прежнему проверяет backend.
- В наборе приёмки исправлена изоляция кеша: новая копия БД не должна проверяться по ID из stale-ответов прошлого прогона. Проверка приоритета учитывает оплаченные промо. Отказы предыдущих запусков не скрывались; окончательный прогон прошёл полностью.

## Нагрузка на последнем коде

Использованы около 5000 товаров, активное продвижение, реальные PostgreSQL/nginx и ответы API. Один и тот же сервер делился с рабочим приложением; у стенда ограничены CPU: backend 1, PostgreSQL 1, nginx 0,5, генератор 0,75. Сборки и unit-тесты во время финальных замеров не выполнялись.

- Основной сценарий: **300 пользователей, 4517 запросов, 0 ошибок, p95 49 мс, p99 83 мс**.
- Расширенный сценарий, включая рейтинг и розыгрыши, после пересоздания nginx с холодным кешем: **300 пользователей, 4521 запрос, 0 ошибок, p95 34,5 мс, p99 48,5 мс**. Поиск p95 51,5 мс, карточка товара 27,9 мс, рейтинг 25,1 мс.
- До исправления запросов расширенный холодный прогон давал p95 2386,2 мс при нуле ошибок; прогретый промежуточный — 155,2 мс. Финальный холодный прогон прошёл заданные пределы 300 мс/1 с.

Это замер 300 пользователей с паузами между действиями, а не обещание любого RPS или неограниченного числа покупателей. Предельный стресс до отказа на общем с production сервере не запускался.
