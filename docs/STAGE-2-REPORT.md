# Этап 2 — Финансовый слой. Отчёт

Дата: 2026-09-13. Всё проверено на локальном стенде.

**Цель:** ядро для денег, на которое лягут TON-оплата, комиссии, escrow, подписки и рефералка. Делается до этапов 3–6, иначе финансовая логика размажется по четырём местам и разойдётся.

---

## Что было

Весь «кошелёк» системы — одно поле `users.referral_earnings` типа `Float`.

Проблемы:
- **`Float` для денег.** Двоичный float не представляет `0.1` точно; при накоплении начислений и делении комиссии погрешность растёт.
- **Одного скалярного поля мало.** Сплит подразумевает нескольких получателей: платформа, автор канала, продавец, реферер. Сущности «партнёр с балансом» не было.
- **Нет истории.** Ответить «из чего сложился баланс» было нельзя.
- **Нет идемпотентности.** Два вебхука по одному заказу = двойное начисление. Защиты не было никакой.
- **Заявка на вывод просто вычитала сумму** из `referral_earnings`. Если её не подтверждали, деньги нигде не числились: с баланса ушли, на вывод не отправились, следа не осталось.

---

## Что сделано

### `services/money.py` — денежная арифметика

Единственное место, где деньги переводятся между хранимым и человекочитаемым видом.

- В БД только целые числа в **минорных единицах**: для TON нанотоны (1e-9), для USD центы.
- `float` в денежных функциях **выбрасывает `TypeError`** — не пролезет даже случайно.
- Проценты в **базисных пунктах**: 2% = 200 bp. Позволяет хранить настройки целыми и не округлять дважды.
- `split_by_bp()` делит сумму на долю и остаток так, что **доля + остаток всегда равны исходной сумме**. Если округлять обе части независимо, на неделимых суммах появляются потерянные или лишние единицы.

Пример из ТЗ заказчика: товар 25 TON, комиссия 2% → 0.5 платформе, 24.5 продавцу. Покрыто тестом.

### `models/finance.py` — счета и журнал

**Настоящая двойная запись.** Кроме счетов пользователей и платформы есть системный счёт `EXTERNAL`, представляющий внешний мир (блокчейн, кошельки вне системы). Деньги не появляются и не исчезают — они приходят с внешнего счёта и уходят на него.

Следствие: **сумма всех проводок в журнале по каждой валюте всегда равна нулю**. Это жёсткий инвариант, на котором строится сверка. Без внешнего счёта такой проверки не существует.

- `accounts` — балансы. Поля `balance_minor` / `hold_minor` — денормализация для быстрого чтения, **источник правды это журнал**.
- `hold_minor` — замороженная часть (escrow, резерв под вывод). Доступно к трате = `balance − hold`.
- `ledger_entries` — неизменяемый журнал. Ошибочная проводка исправляется встречной, а не редактированием.
- Уникальность счёта по (владелец, валюта) — один пользователь может иметь и TON, и USD.

### `services/finance_service.py` — операции

`post()` применяет набор проводок атомарно: либо все, либо ни одной.

**Идемпотентность через `UNIQUE` в БД.** У каждой проводки есть `idempotency_key` вида `ref_type:ref_id:entry_type:account_id`. Проверка «а нет ли уже такой записи» в коде **не работает** — между проверкой и вставкой пролезает параллельный запрос. Только `UNIQUE` даёт настоящую защиту.

Балансы двигаются атомарным `UPDATE ... SET balance = balance + :delta`, а не чтением-записью в Python — иначе два параллельных начисления затрут друг друга.

Типовые операции: `deposit_from_external`, `transfer`, `withdraw_to_external`, `hold`, `release_hold`.

Защита от ухода в минус: любой счёт, кроме `EXTERNAL`, не может иметь отрицательный баланс или заморозку больше баланса.

### `services/settings_service.py` — настройки из админки

Всё, что заказчик должен менять сам, переезжает в таблицу `app_settings`: проценты комиссий и рефералки, пороги антифрода, сроки. Раньше реферальный процент был зашит в `REFERRAL_PERCENTAGE` в `.env` — поменять означало править файл на сервере и перезапускать контейнер.

- 13 ключей описаны в реестре `SETTING_DEFS` — тип, дефолт, границы, описание.
- Значения из БД перекрывают дефолты; отсутствие ключа не ошибка.
- **Валидация по границам:** выставить комиссию 200% или отрицательный срок через API нельзя.
- Кеш в памяти процесса, сбрасывается при записи.

### Перенос существующих балансов (миграция `d9e3f4a5b6c7`)

`users.referral_earnings` → счета + журнал, с встречной проводкой на внешний счёт.

**Решение по валюте.** Старые балансы номинированы в USD, новые начисления пойдут в TON. Пересчитывать историю по сегодняшнему курсу — значит задним числом менять людям суммы и потом объясняться. Поэтому старые остатки перенесены **как USD**, TON начнёт начисляться с нуля. Счёт умеет обе валюты.

> Это моё решение по открытому вопросу №3 из плана. Если заказчик захочет иначе — переиграть можно, но обсудить лучше до появления реальных TON-балансов.

Проверено на данных с намеренно неудобными значениями: `12.34` → ровно 1234 цента, float-артефакт `0.1 + 0.2` (`0.30000000000000004`) → ровно 30 центов.

Само поле `referral_earnings` **не удалено**: его отдаёт API и читает фронт. Теперь это денормализованный кеш, который поддерживает финансовый слой. Удалить можно после перехода фронта на новые эндпоинты.

### Рефералка и выводы переведены на журнал

Чтобы не было двух источников правды, существующая логика подключена сразу.

**`referral_service`:**
- процент из настроек вместо зашитых 3%;
- расчёт целочисленный, в центах;
- начисление идемпотентно — повторный вебхук не удвоит;
- убран `db.commit()` изнутри: функция вызывается из `complete_order()` внутри его транзакции, и коммитить чужую транзакцию на середине нельзя — при последующей ошибке откатывать уже нечего.

**Выводы:** заявка теперь **замораживает** сумму, а не вычитает её. Списание происходит при подтверждении админом. Повторное подтверждение не списывает дважды (проверено).

### Админские эндпоинты

`GET/PUT /api/admin/settings`, `GET /api/admin/finance/accounts`, `GET /api/admin/finance/ledger`, `POST /api/admin/finance/reconcile`. UI появится на этапе 7.

### Сверка

`finance_service.reconcile()` проверяет два независимых инварианта:
1. по каждому счёту: `balance_minor` == сумме проводок;
2. по каждой валюте: сумма **всех** проводок == 0.

Расхождение означает, что деньги двигали в обход финансового слоя. Добавлена ежедневная джоба в APScheduler: при несходе шлёт алерт админу в Telegram.

### Тесты — первые в проекте

Инфраструктура: pytest + pytest-asyncio, отдельная тестовая база, каждый тест в откатываемой транзакции.

**39 тестов, все проходят.** Покрыто:
- конверсии, округления, запрет `float`, float-артефакты;
- деление комиссии — в том числе параметризованный тест «ничего не теряется» на неделимых суммах;
- двойная запись и отказ от несбалансированной операции;
- идемпотентность: повторный вебхук, двойное подтверждение вывода;
- работоспособность сессии после отката по дубликату (иначе повторный вебхук ронял бы всю обработку заказа);
- заморозка: две заявки на вывод не могут превысить баланс;
- сверка, включая обнаружение правки баланса в обход журнала.

## Найдено попутно

**Реферальная статистика показывала почти нули.** `get_referral_statistics()` считала заказы фильтром `status == "paid"`. Но `complete_order()` для цифровых товаров и инструкций сразу переводит заказ в `completed` — под фильтр попадали только услуги, ждущие ручной обработки. То есть в разделе «мои рефералы» у пользователей не отображалось большинство покупок. Исправлено на `in_(["paid", "completed"])`.

Там же был **N+1**: запрос за заказами выполнялся внутри цикла по рефералам. Переписано на два запроса с раскладкой в памяти.

## Открытые вопросы

1. **Валюта старых балансов** — перенёс как USD (обосновано выше). Нужно подтверждение заказчика.
2. **Источник реферального начисления.** Сейчас `EXTERNAL`, потому что оплата заказов идёт мимо журнала (CryptoBot). На этапе 3, когда платежи начнут зачисляться на счёт платформы, источником станет он.
3. **Второй уровень рефералов** — настройка `referral_l2_bp` заведена (по умолчанию 0 = выключен), сама логика в этапе 6: нужна колонка `level` в `referral_transactions`.
