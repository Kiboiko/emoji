# Этап 3 — проект архитектуры

Дата: 01.11.2026. **Статус: план утверждён пользователем 01.11.2026; реализация разрешена. Выкатка и реальные внешние действия отдельно не разрешены.**
Требования: пункты 8–10 нового ТЗ от 19 октября. Старая нумерация WORK_PLAN.md относится к другим работам.

## 1. Объём

- Недельный рейтинг маркетов по продажам и отзывам; рамки золото/серебро/бронза для первых трёх мест. Администратор управляет показом на главной; объём продаж видит только он.
- Публикация крупных завершённых сделок в отдельный Telegram-чат: товар, фото, магазин, цена, ссылка.
- Бесплатные розыгрыши NFT-подарков с проверкой подписок на все заданные каналы/чаты, случайным выбором и показом победителя.

Использовать существующие FastAPI, PostgreSQL, React и APScheduler. Состояния и очередь хранить в PostgreSQL; Redis, Celery и новые серверы не нужны. Работать одной моделью Sol без подагентов. Проверки первого этапа остаются открытыми; пользователь просит общую приёмку после реализации третьего.

## 2. Опорные точки существующего кода

- SellerProfile, Deal, RELEASED/REFUNDED, `released_at`, суммы в нанотонах: `backend/models/p2p.py`.
- `services/deal_service.py::_release_to_seller`: финансовое завершение P2P. Событие публикации записывать в той же транзакции, не добавляя commit в helper.
- `models/review.py`: есть `deal_id`, `is_hidden`, `is_fake`, время. Накопительные counters SellerProfile не являются недельными показателями.
- `services/catalog_service.py::completed_sale_condition`, `routes/sales_feed.py`: уже отделяют завершённую продажу от оплаты/escrow/отмены. Не учитывать продвижение как продажу товара.
- `routes/stores.py`: строка магазинов на главной показывает продавцов и площадку. Каналы намеренно представлены отдельно через товары подписок и свои витрины; не добавлять их в строку магазинов ради рейтинга.
- `services/telegram_service.py`: переиспользовать транспорт Bot API и маскирование токена.
- `services/scheduler.py`: задачи работают в процессе backend, поэтому защиту повторов делать через UNIQUE и блокировки БД.
- `services/audit_service.py`, `utils/auth.py`: новые настройки только require_admin. Доступ модератора не расширять.
- Frontend StoreStrip, страницы магазина, темы и `lib/productLink.ts`: использовать готовые карточки и Telegram-ссылки.

## 3. Утверждённые решения

1. Неделя: понедельник 00:00 — следующий понедельник 00:00 Europe/Moscow. В БД UTC, интервалы [start, end).
2. В рейтинге участвуют выбранные администратором пользовательские маркеты; площадка и отдельные каналы вне конкурса. Число участников не ограничивать жёстко десятью; на главной по умолчанию топ-10.
3. Утверждённая формула: 70% оборот завершённых продаж за неделю, 30% качество реальных отзывов на эти сделки. `V` — USD-центы из снимков покупок; `Q=(sum(rating)+5*3)/(n+5)`; `score=70*(V/Vmax)+30*(Q/5)`. Если Vmax=0, вклад продаж нулевой; магазины без продаж ниже продавших. Равенство разрешают оборот, Q, стабильный UUID. Денежные величины — integer/Decimal.
4. Для конкурса учитывать только подтверждённые отзывы выпущенных сделок этой недели, не hidden/fake. Обычный рейтинг за 30 дней на карточках не менять. Поздние отзывы не переписывают закрытую неделю.
5. Крупная сделка — одна завершённая P2P-сделка; порог по полной сумме Deal.amount_nano, с количеством, до комиссии. Сам порог задаёт владелец; до настройки функция выключена.
6. Один розыгрыш — один подарок и один победитель. Владелец выдаёт подарок вручную, приложение хранит отметку выдачи. Автоматическая передача NFT/Stars, хранение приватного ключа и списание активов в этот проект решения не входят.

Пользователь утвердил план, формулу 70/30 и ручную выдачу 01.11.2026. Порог/чат публикаций и данные розыгрыша настраиваются позже; новые внешние действия по умолчанию выключены.

## 4. Рейтинг и управление главной

**Модели:** SellerProfile.home_visible default true, ranking_enabled default false. Поле видимости Channel не требуется: каналов нет в существующей строке магазинов. Старые магазины остаются на главной, в конкурс никто не включается автоматически.

`market_ranking_periods`: start/end, open/closed, версия/параметры формулы, updated_at, closed_at; UNIQUE(start_at). `market_ranking_entries`: period_id + seller_profile_id UNIQUE, место, score, оборот в центах, количество продаж, сумма/число оценок, Q. Исторические ссылки RESTRICT, без каскадного удаления архива.

При открытии недели фиксировать состав участников. Изменение ranking_enabled влияет на следующую неделю. home_visible/блокировка действуют сразу, но не пересчитывают архив и не передают чужую медаль: публичная выдача просто исключает скрытый магазин. Пустые/заблокированные магазины не становятся доступными благодаря рейтингу.

Задача раз в 5 минут агрегирует данные без N+1 под advisory lock периода. На границе недели закрывает старый период и открывает новый; после простоя догоняет пропущенные границы с последним наблюдавшимся составом для пропущенных полных недель. Текущая неделя использует актуальные флаги участия. Первичное включение не создаёт задним числом историю конкурсов. Закрытые периоды неизменяемы; исправления — отдельным аудируемым решением. Формулу посреди периода не менять.

Главная показывает текущий рейтинг с периодом/updated_at; архив — отдельно. Public DTO: имя/аватар магазина, id, место, medal, обычный публичный рейтинг и границы периода. **Никакого оборота, внутренних score/денежных агрегатов или покупателей.** Для администратора отдельная схема с объяснением расчёта. Кеш главной не дольше существующих 3 секунд nginx; персональные ответы не кешировать.

API: GET `/api/market-rankings/current`, GET `/api/market-rankings/periods/{id}`, admin API управления участием/показом. Существующий GET `/api/stores` сохраняет форму и получает только безопасные optional-поля места/медали. Площадка/каналы сохраняются как прежде, но медалей не получают. Новые admin-действия журналируются, модератору закрыты.

## 5. Крупные сделки: транзакционная очередь

`telegram_publications`: UNIQUE(kind, source_id, destination_chat_id), публичный payload, status, attempts, next_attempt_at, lease_until, telegram_message_id, безопасный error_code, created/sent_at. Состояния pending → sending → sent; отдельно retry/failed/unknown/suppressed.

В транзакции перехода RELEASED при включённом правиле создаётся событие. HTTP-обработчик не отправляет сообщение до commit. Публикации по умолчанию выключены, старые сделки задним числом не рассылаются. Сохранить enabled_at. При отключении/смене чата приостановить старые задания, не перенаправлять их автоматически.

Dispatcher раз в 15–30 секунд забирает небольшую пачку `FOR UPDATE SKIP LOCKED`, фиксирует lease, отпускает транзакцию и вызывает Telegram. Учитывает 429/retry_after, ограничивает повторы; успех сохраняет message_id. Сбой Telegram не откатывает продажу или расчёты.

**Не обещать exactly-once при неопределённом исходе отправки.** Timeout/обрыв после возможного принятия и просроченный sending после падения переводить в unknown. Повтор — после сверки администратором, иначе возможен дубль. Определённый отказ и явный retry_after допускают автоматический повтор. Это часть тестов и инструкции.

Фото брать из безопасного uploads или Telegram file_id, не скачивать произвольные внешние адреса. Если фото нет — текст с той же ссылкой. Fallback после sendPhoto допустим при определённом отказе, не при timeout. Экранировать пользовательский текст; не публиковать контакты, buyer id, инструкции, переписку.

Настройки: enabled=false, положительный min_nano, chat_id/topic, enabled_at. На форме цена в Gram с точным переводом в нанотоны. Получатель только в admin-схеме, не PublicSettings. Для включения нужны выбранный чат и права бота. API/UI: config, preview **без отправки**, preflight прав, журнал, решение unknown. Реальный пробный пост — только явное действие администратора.

## 6. Розыгрыши

**Данные:** giveaways (ru/en, приз/фото, start/end UTC, status/version, winner_user_id, безопасное public_winner_label, draw timestamps, snapshot_count/hash, fulfillment_status); required_chats (BIGINT chat_id, публичное имя, join_link, UNIQUE giveaway+chat); entries (UNIQUE giveaway+user, entered/checked_at, статус/код причины); draw_attempts (entry_id, ordinal, результат; UNIQUE giveaway+entry и giveaway+ordinal). Приватные ключи не хранить.

**Состояния:** draft → scheduled/open → drawing → finished (приём заявок закрывается по end_at до запуска drawing); waiting_for_telegram — возобновляемое ожидание, cancelled — финал. Ноль подходящих участников: finished без winner. После публикации условия, приз и дедлайн фиксируются; незаметное редактирование или перезапуск завершённого розыгрыша запрещены. Для исправлений — видимая отмена и новый розыгрыш до финала.

**Участие:** идентичность из Telegram-авторизации backend, клиент не задаёт чужой telegram_id и результат подписки. До публикации бот должен быть администратором во всех обязательных чатах. Потеря прав/ошибка API — unknown, а не «пользователь не подписан» и не автоматический допуск.

getChatMember: member/administrator/creator подходят, restricted — только is_member=true; left/kicked — нет. Проверки ограничены по частоте/конкуренции, кеш короткий. Не держать row lock во время сети: после проверки в короткой транзакции повторно проверить version/status/deadline и вставить одну заявку. После end_at вход закрыт. Пользователь видит условия и ссылки; согласие на безопасное отображение победителя раскрывается до участия. Полные Telegram ID и список участников публично не выдавать.

**Выбор:** в конце фиксируются заявки до дедлайна, count и digest набора. Из оставшихся кандидатов равномерно выбрать через secrets.randbelow; сохранить draw_attempt ДО сетевой перепроверки. Проверить блокировку и свежую подписку на все чаты. Точно отписавшегося исключить с причиной, выбрать следующего из оставшихся. Сетевой сбой — повтор того же кандидата, не новый выбор.

Один draw на розыгрыш через DB lock/lease. После падения возобновлять сохранённую попытку. Winner и finished фиксируются атомарно; повтор запроса возвращает тот же результат. Кнопки «перевыбрать» завершённого победителя нет. Отправка уведомления не является условием выбора и не запускает новый draw при ошибке. Выдача подарка — отдельная ручная отметка admin.

Проверяется членство в момент проверки кандидата, а не исторический снимок точно на дедлайн. Без отдельного публичного протокола/внешней случайности не обещать независимую криптографическую доказуемость розыгрыша; журнал объясняет действия сервера.

API: public list/detail (приз/условия/срок/число заявок/итог); auth my-entry/join/check-membership; admin draft CRUD/preflight/publish/cancel/progress/участники/выдача. Клиент не передаёт seed/index/winner. Frontend: список, карточка, условия, участие, повтор подписки, восстановление статуса, результат. Admin: редактор, права бота, участники с пагинацией, ошибки, история, отметка выдачи. ru/en, light/dark, мобильный экран; новые разделы закрыты модератору.
