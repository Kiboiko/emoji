# Приёмочные испытания

Набор, который прогоняет всю систему «как у клиента»: настоящие HTTP-запросы
через настоящий nginx к настоящему образу бэкенда, на **копии боевой базы**.
Боевые контейнеры, база и файлы не затрагиваются.

Запускать после любых заметных изменений и перед сдачей этапа. Результаты
последнего прогона — в [docs/ACCEPTANCE-STAGE-1.md](../docs/ACCEPTANCE-STAGE-1.md).

## Что внутри

| Файл | Назначение |
|---|---|
| `stage_up.sh` | Поднимает одноразовый стенд: свежий дамп боевой базы → временная база, миграции, образ бэкенда из `/opt/marketplace/backend`, nginx с боевым конфигом и боевыми сборками фронтенда и админки |
| `acceptance.py` | Приёмочные сценарии: каждый пункт этапа 1, права по всем маршрутам, безопасность, нагрузка живых пользователей. Печатает `PASS`/`FAIL` |
| `run_backend.py` | Запуск бэкенда на стенде. Telegram наружу **не уходит**: отправки пишутся в файл, чтобы проверить текст и получателей |
| `stage_run.sh` | Запускает `acceptance.py` внутри сети стенда и проверяет логи бэкенда (токен бота в них быть не должен) |
| `stage_load.sh`, `load.js`, `mint_tokens.py` | Нагрузочные испытания на k6: живые пользователи, всплеск, предел пропускной способности |
| `bench.py` | Замер одного маршрута: запросов в секунду и задержка |
| `stage_down.sh` | Убирает стенд |

## Как запустить

Нужен сервер с Docker и проектом в `/opt/marketplace` (как на боевом сервере).

```bash
mkdir -p /opt/acc/code && cp acceptance/* /opt/acc/code/     # скрипты стенда
bash /opt/acc/code/stage_up.sh        # 3–5 минут: образ, копия базы, миграции, nginx
bash /opt/acc/code/stage_run.sh       # ~1,5 минуты: приёмочные сценарии
bash /opt/acc/code/stage_load.sh      # ~3,5 минуты: нагрузка на k6 (образ grafana/k6 скачивается сам)
bash /opt/acc/code/stage_down.sh      # убрать стенд
```

Итог `stage_run.sh` — строка `ИТОГ: N из N проверок пройдено`. Если есть
`FAIL`, под ней перечислено, что не прошло. Код возврата 0 — всё прошло.

Параметры нагрузки (переменные окружения): `LOAD_USERS_REAL` (по умолчанию 300
живых пользователей), `LOAD_SECONDS` (50).

## Как это устроено и чего не делает

* **Данные.** Стенд — копия боевой базы на момент запуска. Тестовые пользователи,
  заявки, отзывы создаются в копии и удаляются вместе со стендом.
* **Telegram.** Бот в стенде настроен на поддельный токен, исходящие сообщения
  пишутся в файл. Реальные люди ничего не получают. Единственный настоящий
  запрос к Telegram — публикация отзыва в канал (с поддельным токеном он
  заведомо падает): по нему проверяется, что токен не попадает в логи.
* **Заголовок X-Forwarded-For.** На стенде нет Caddy, поэтому тест лимита попыток
  входа подставляет адрес этим заголовком. На боевом сервере его ставит Caddy
  из настоящего соединения, и подделать его снаружи нельзя.
* **Нагрузка.** Для измерения предела нужен эффективный генератор (k6): Python
  упирается в своё ядро на 150–250 запросах в секунду и показывает не
  задержку сервера, а свою. Цифры снимаются на том же сервере, где работает
  сайт, поэтому клиент и сервер делят ядра — это занижает результат.
* **Чего здесь нет.** Интерфейс приложения в Telegram (проверяется вручную на
  телефоне), настоящие платежи в блокчейне, рассылки реальным пользователям.
