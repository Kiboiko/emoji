## Проверка актуального кандидата этапов 1–3

Новые `verify_up.sh`, `verify_run.sh`, `verify_down.sh` используют контейнеры/сети
`gram-verify-*`, PostgreSQL 17, отдельную тестовую БД, захват всех HTTP-вызовов
Telegram/TON и локальный nginx на 18083. Backend/БД не имеют внешней сети.
Рабочие контейнеры, код и тома не заменяются. `verify_up` только читает дамп и uploads
из существующего deployment. Нужен заранее подготовленный актуальный кандидат в
`$VERIFY_ROOT/candidate` без `.env`, приватной истории и node_modules — старого HEAD
недостаточно, пока изменения этапов не оформлены коммитами.

```bash
export VERIFY_ROOT=/opt/gram-verify-20261101
bash "$VERIFY_ROOT/candidate/acceptance/verify_up.sh"
bash "$VERIFY_ROOT/candidate/acceptance/verify_run.sh"
# Отдельный расширенный load, когда не идут сборки и другие тесты:
# python /acc/project_load.py внутри runner с теми же mounts/env/network.
bash "$VERIFY_ROOT/candidate/acceptance/verify_down.sh"
```

При повторном восстановлении БД пересоздайте также тестовый nginx: его старый кеш
содержит ID предыдущего набора. HTTP-набор использует свежие ответы для подготовки
данных нагрузки и уникальный ключ для собственной проверки кеша.

`growth_http.py` записывает управляющие ответы в тестовый outbox и запускает
серверную финализацию там же, где scheduler. Он отказывается работать вне заданного
изолированного окружения. `project_load.py` добавляет рейтинг/розыгрыши в смесь из
300 пользователей. Результаты/покрытие сохраняются в artifacts/outbox; до очистки
сохраните обезличенные JSON. Cleanup удаляет БД и копии uploads/outbox, исходники
и закрытые журналы остаются. Сырые копии данных не публиковать.

`candidate-ui.cjs` проверяет собранные приложения с настоящим API стенда через
локальный SSH-туннель на 18084; проверяет testnet и тестовый manifest, использует
искусственный Telegram initData. Запуск из корня: `node acceptance/candidate-ui.cjs`.
Нужны Playwright и браузер (`PLAYWRIGHT_MODULE`, `BROWSER_CHANNEL=msedge` при необходимости).
Тестовый пароль после HTTP-набора задан в сценарии; для другого окружения доступны
`VERIFY_ADMIN_USER`/`VERIFY_ADMIN_PASSWORD`. Метаданные кошельков подменяются.
Это не вход настоящим клиентом Telegram и не настоящая оплата.

Общая приёмка этапов 1–3 подготовлена в [чек-листе](../docs/ACCEPTANCE-STAGES-1-3.md).
Этап 3 пока не выложен: существующий `stage_up.sh` берёт код из `/opt/marketplace`,
поэтому перед общей приёмкой направьте сборку на актуального кандидата.

Для отдельного browser smoke этапа 3 есть `stage3-ui-smoke.cjs`. Запуск из корня
репозитория после `npm ci` в frontend/admin: `node acceptance/stage3-ui-smoke.cjs`.
Нужны установленный Playwright и его Chromium; `PLAYWRIGHT_MODULE` позволяет задать
путь к модулю, `BROWSER_CHANNEL=msedge` — использовать Edge. Скрипт запускает локальные
Vite на 4175/4176, подменяет API и сохраняет снимки в `.tmp/`; Telegram и серверные
изменения не выполняются. Это не общий HTTP/nginx и нагрузочный прогон.

Набор, который прогоняет всю систему «как у клиента»: настоящие HTTP-запросы
через настоящий nginx к настоящему образу бэкенда, на **копии боевой базы**.
Боевые контейнеры, база и файлы не затрагиваются.

Запускать после любых заметных изменений и перед сдачей этапа. Результаты
последнего прогона — в [docs/ACCEPTANCE-STAGE-1.md](../docs/ACCEPTANCE-STAGE-1.md).

## Что внутри

| Файл | Назначение |
|---|---|
| `stage_up.sh` | Поднимает одноразовый стенд: свежий дамп боевой базы → временная база, миграции, образ бэкенда из `/opt/marketplace/backend`, nginx с боевым конфигом и боевыми сборками фронтенда и админки |
| `acceptance.py` | Приёмочные сценарии: каждый пункт этапа 1, права по всем маршрутам, безопасность, нагрузка живых пользователей. Печатает `PASS`/`FAIL` |
| `run_backend.py` | Запуск бэкенда на стенде. Telegram наружу **не уходит**: отправки пишутся в файл, чтобы проверить текст и получателей |
| `stage_run.sh` | Запускает `acceptance.py` внутри сети стенда и проверяет логи бэкенда (токен бота в них быть не должен) |
| `stage_load.sh`, `load.js`, `mint_tokens.py` | Нагрузочные испытания на k6: живые пользователи, всплеск, предел пропускной способности |
| `bench.py` | Замер одного маршрута: запросов в секунду и задержка |
| `stage_down.sh` | Убирает стенд |

## Как запустить

Нужен сервер с Docker и проектом в `/opt/marketplace` (как на боевом сервере).

```bash
mkdir -p /opt/acc/code && cp acceptance/* /opt/acc/code/     # скрипты стенда
bash /opt/acc/code/stage_up.sh        # 3–5 минут: образ, копия базы, миграции, nginx
bash /opt/acc/code/stage_run.sh       # ~1,5 минуты: приёмочные сценарии
bash /opt/acc/code/stage_load.sh      # ~3,5 минуты: нагрузка на k6 (образ grafana/k6 скачивается сам)
bash /opt/acc/code/stage_down.sh      # убрать стенд
```

Итог `stage_run.sh` — строка `ИТОГ: N из N проверок пройдено`. Если есть
`FAIL`, под ней перечислено, что не прошло. Код возврата 0 — всё прошло.

Параметры нагрузки (переменные окружения): `LOAD_USERS_REAL` (по умолчанию 300
живых пользователей), `LOAD_SECONDS` (50).

## Как это устроено и чего не делает

* **Данные.** Стенд — копия боевой базы на момент запуска. Тестовые пользователи,
  заявки, отзывы создаются в копии и удаляются вместе со стендом.
* **Telegram.** Бот в стенде настроен на поддельный токен, исходящие сообщения
  пишутся в файл. Реальные люди ничего не получают. Единственный настоящий
  запрос к Telegram — публикация отзыва в канал (с поддельным токеном он
  заведомо падает): по нему проверяется, что токен не попадает в логи.
* **Заголовок X-Forwarded-For.** На стенде нет Caddy, поэтому тест лимита попыток
  входа подставляет адрес этим заголовком. На боевом сервере его ставит Caddy
  из настоящего соединения, и подделать его снаружи нельзя.
* **Нагрузка.** Для измерения предела нужен эффективный генератор (k6): Python
  упирается в своё ядро на 150–250 запросах в секунду и показывает не
  задержку сервера, а свою. Цифры снимаются на том же сервере, где работает
  сайт, поэтому клиент и сервер делят ядра — это занижает результат.
* **Чего здесь нет.** Интерфейс приложения в Telegram (проверяется вручную на
  телефоне), настоящие платежи в блокчейне, рассылки реальным пользователям.
