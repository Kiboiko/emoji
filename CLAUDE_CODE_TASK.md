# Задание для Claude Code — доработка Marketplace (Telegram Mini App)

## Контекст проекта

Существующий маркетплейс, доставшийся от предыдущего разработчика. Код рабочий и в целом качественный, но с критичными проблемами безопасности и техдолгом. Стек:

- **Backend:** Python 3.13, FastAPI, SQLAlchemy 2.0 (async), PostgreSQL 17, Alembic, APScheduler
- **Frontend (витрина):** React 19 + TypeScript, Vite, framer-motion
- **Admin:** отдельное React + TypeScript приложение
- **Оплата сейчас:** CryptoBot (`aiocryptopay`) — подлежит замене
- **Инфраструктура:** Docker (docker-compose), nginx

**Важно:** это боевой проект с реальными данными и платежами. Любые изменения структуры БД должны быть безопасными и обратимыми. Ничего не ломать в существующей логике товаров/заказов.

## ЭТАП 2 — Замена CryptoBot → TON Connect

### Что известно из аудита
- Оплата частично изолирована: `services/payment_service.py` (`CryptoBotService`).
- `complete_order()` — **единственная точка выдачи товара** — про CryptoBot не знает, переиспользуется как есть.
- Проблема: выпуск инвойса вшит в тело `create_order`, и **на каждую позицию корзины создаётся отдельный заказ** → с TON Connect это N подписей в кошельке за один checkout.
- `price_ton` в админке не редактируется; конвертацию USD→TON надо делать самим.

### Задачи
1. **Объединить корзину в один платёж** (согласовано с заказчиком): один checkout = одна транзакция = одна подпись в кошельке. Переработать `create_order`, чтобы заказ агрегировал все позиции корзины, а не плодил заказы по одной.
2. **Новый модуль оплаты TON Connect** (по аналогии с изоляцией CryptoBot — вся логика в одном сервисе):
   - Генерация транзакции для подписи кошельком (сумма, адрес получателя-платформы, payload с идентификатором заказа)
   - Возврат транзакции фронту для передачи в TON Connect
   - **Проверка транзакции on-chain** по хэшу: подтвердить, что платёж реально прошёл, на нужный адрес и сумму — только тогда вызывать `complete_order()`. Не доверять фронту.
3. **Курс USD→TON:** реализовать источник курса (внешний API), с «заморозкой» курса на момент создания заказа (чтобы сумма не плавала между показом цены и оплатой). Согласовать источник и TTL заморозки.
4. **Редактирование цен в админке:** добавить возможность управлять ценами/курсовой логикой из админ-панели.
5. **Обработка edge-кейсов:** недоплата, просроченная транзакция, оплата после автоотмены заказа (согласовать поведение), повторная отправка того же платежа (идемпотентность).
6. Удалить/отключить CryptoBot-код и зависимость `aiocryptopay` после переноса.

## ЭТАП 3 — Подписки на закрытые каналы

### Что известно из аудита
- Подписок нет вообще — ни модели, ни строчки.
- Бот умеет только `/start`, работы с каналами нет.
- APScheduler уже подключён — джобы истечения лягут туда.
- **Финслой не готов под сплит:** баланс — одно поле `Float` на юзере, `ReferralTransaction` жёстко под 3% рефералки, сущности «партнёр/автор» нет. Нужен настоящий финансовый слой.

### Задачи
1. **Модель подписок:** подписка, тариф (сроки 1/3/6/12 мес), привязка к закрытому каналу/группе автора, статусы (активна/истекает/истекла).
2. **Автовыдача доступа:** после подтверждённой оплаты бот выдаёт доступ в закрытый канал автора. **Важное ограничение Telegram:** бот не может принудительно добавить пользователя в канал по `user_id` — выдавать доступ через персональную одноразовую invite-ссылку (`createChatInviteLink` с ограничением на использование). Бот должен быть админом канала.
3. **Автоотзыв доступа:** по истечении подписки — удаление пользователя из канала (`banChatMember`/`unbanChatMember` для kick) через джобу APScheduler.
4. **Уведомления:** заранее о скором окончании подписки, об окончании.
5. **Сплит комиссии:** переработать финслой — ввести сущность автора/партнёра, отделить баланс платформы от баланса авторов, реализовать удержание комиссии платформы (процент настраивается в админке). Выплаты авторам — вручную (согласовано).
6. **Каталог/карточки авторов и подписок** (см. ранее проработанное ТЗ: каталог, скрытие настоящего @username, продвижение объявлений).

> Часть «сплит комиссий» — самая тяжёлая, ~3.5 дня, может быть вынесена отдельным под-этапом.

## ЭТАП 4 — P2P-маркетплейс (пользователи продают свои товары)

### 4.1. Размещение товаров пользователями
- Пользователь отправляет **заявку** на размещение: название, описание, фото, своя цена.
- Товар уходит на **модерацию** (одобрить/отклонить в админке).
- После одобрения — публикуется с обязательной **пометкой «товар другого пользователя»** (визуально отличать от товаров платформы).
- **Антифрод:** блокировка пользователя за частые заявки / много отказов (задать пороги, настраиваемые в админке).
- **Отзывы о товаре** — добавить возможность оставлять.

### 4.2. Escrow-сделка через бота (ядро P2P)
Логика после покупки P2P-товара:
1. Платформа принимает оплату и **держит деньги** (escrow), не переводя продавцу сразу.
2. Бот создаёт отдельный чат для сделки: **форум-топик** (`createForumTopic` в группе-форуме) либо отдельную группу.
3. **Добавление участников:** напрямую по `user_id` Telegram не позволяет — бот **отправляет обоим (продавцу и покупателю) invite-ссылку** на этот чат/топик. Возможность связаться появляется только после покупки.
4. В чате стороны договариваются, платформа наблюдает как третья сторона.
5. Покупатель **подтверждает получение** → только после этого продавец получает деньги (выплата **вручную**, по принципу подписки).
6. Проблемы покупатель обязан сообщить **до** подтверждения. Споры решаются по правилам платформы. Возвраты — **вручную**.
7. **Нарушение условий → блокировка** пользователя.

### 4.3. Условия платформы
- Отдельная страница с условиями использования.
- Перед покупкой — **чекбокс согласия** у покупателя; у продавца — при размещении товара. Без согласия действие недоступно.

### Технические заметки по этапу 4
- Бот должен быть админом в группе-форуме, где создаются топики сделок.
- Продумать состояния сделки (создана → оплачена/escrow → чат создан → подтверждена → выплачено / спор / возврат) как конечный автомат.
- Идемпотентность: одна покупка = один топик, без дублей.

## Сквозные требования (для всех этапов)

1. **Не ломать существующее:** товары, заказы, текущие пользователи должны продолжать работать на каждом шаге.
2. **Миграции только безопасные:** каждое изменение схемы — через Alembic, с проверкой, что не сносит данные.
3. **Логирование вместо print:** в проекте ~60 `print()` — заменять на нормальное логирование по мере касания файлов.
4. **Идемпотентность денежных операций:** оплата, выдача товара, выплаты — защита от двойного срабатывания.
5. **Финансовые операции проверяются on-chain / по факту**, а не по слову клиента.
6. **Каждый этап — законченный кусок:** можно принять и протестировать отдельно.
7. **`.env` с разделением тестовых/боевых значений** + обновлять инструкцию по деплою.
